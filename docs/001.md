목표는 이거다.

> 런타임에서 맞기 전에, 코딩 중에 Next.js 의미론 오류·성능 위험·운영 위험을 IDE가 미리 잡아준다.

Next.js 공식 TypeScript plugin도 segment config 값, `use client` 사용, client hook 사용 같은 일부는 잡지만 범위가 제한적이다. Next의 `fetch`는 서버에서 persistent cache/revalidation 의미까지 확장되고, App Router는 파일 시스템 convention과 Server Components/Suspense/Server Functions를 기반으로 동작한다. 그래서 “표준을 깊게 이해한 정적 DX 엔진” 여지가 있다.

## 1. 추가적인 킬러 피쳐 제안

### A. Partial Prerendering (PPR) Boundary 추론

Next.js의 미래는 PPR에 있습니다. 단순히 Static/Dynamic을 나누는 게 아니라, "어디서부터 정적 쉘이 깨지고 동적 렌더링으로 전환되는가"를 시각화해야 합니다.

- **기능:** `Suspense` 경계 내부에서 `cookies()`나 `searchParams`를 사용할 때, 해당 `Suspense`가 `fallback`을 트리거하는 지점을 하이라이트.
    
- **효과:** 개발자가 의도치 않게 페이지 전체를 Dynamic으로 만드는 실수를 방지.
    

### B. `redirect` inside `try-catch` 안티 패턴 검사

Next.js의 `redirect()`는 내부적으로 `NEXT_REDIRECT` 에러를 throw하여 동작합니다. 이걸 모르고 `try-catch`로 감싸면 리다이렉트가 동작하지 않는 버그가 생깁니다.

- **검사:** ```typescript
    
    try {
    
    redirect('/login')
    
    } catch (e) {
    
    // 여기서 리다이렉트가 먹혀버림
    
    }
    
- **알림:** `redirect()` should be called outside of try-catch blocks.
    

### C. Request Waterfall 분석 (Static Analysis)

한 서버 컴포넌트 내에서 여러 개의 `await fetch`가 직렬로 나열된 경우를 감지합니다.

- **표시:** "Sequential fetches detected. This will cause a waterfall of $N$ms."
    
- **추천:** `Promise.all()` 사용 권장 또는 `Suspense` 분리 제안.
    

### D. `server-only` 패키지 강제 및 Taint API 가드

보안 측면에서 `import "server-only"`가 누락된 채로 DB 클라이언트나 시크릿 로직이 작성되는 것을 감지합니다.

- **기능:** 특정 폴더(예: `lib/server`)의 파일이 `use client` 하위 트리로 유입될 때 즉시 경고.
    
- **React Taint API 지원:** `taintUniqueValue` 등으로 보호된 데이터가 클라이언트로 전달되는 경로 추적.
    

### E. Next.js 15+ Breaking Change 미리보기

Next 15부터 `params`, `searchParams`가 `Promise`로 변경되는 등 파괴적 변경사항이 많습니다.

- **기능:** 현재 코드가 차세대 Next.js 버전의 런타임에서 깨질지 여부를 미리 체크.

## 3. 기술적 제언: "Next.js 전용 정적 분석의 한계 돌파"

Next.js는 파일 시스템이 곧 API인 프레임워크이기에, 표준 LSP만으로는 부족합니다.

1. **Virtual File System Overlay:** IDE 상의 파일 트리와 Next.js의 Route Group `()`, Parallel Routes `@`를 결합한 가상 맵을 상시 유지해야 합니다.
    
2. **Cross-file Type Flow:** Server Action의 인자 타입이 클라이언트 Form에서 어떻게 직렬화되는지 추적하려면 단순한 TS 타입 체크 이상의 'Data Flow Analysis'가 필요합니다. (LATTICE의 강점을 여기서 발휘하십시오.)
    
3. **Config Combination Matrix:** `export const dynamic = 'force-static'`과 `fetch(..., {cache: 'no-store'})`가 충돌할 때 Next.js가 내리는 최종 결정을 시뮬레이션하는 결정론적 엔진이 핵심입니다.

---

# 1. 판정 대신 Evidence

## ❌ 나쁜 방식

```
❌ This route is dynamic
```

→ 틀리면 바로 신뢰 깨짐

---

## ✔ 좋은 방식

```
⚠️ Possibly dynamic (?)Evidence:- cookies() used in layout.tsx- fetch(..., { cache: 'no-store' }) in page.tsx- searchParams accessedConfidence: Medium
```

---

# 2. “?” UX 패턴

이렇게 계층 나눠라:

```
✔ Static (High confidence)⚠️ Dynamic (?) (Medium)❓ Unknown (?) (Low)
```

---

# 3. Evidence 종류

각 기능마다 evidence를 쪼개야 함

---

## 3.1 Rendering (SSR/ISR/Dynamic)

```
⚠️ Dynamic (?)Evidence:- app/layout.tsx → cookies()- app/dashboard/page.tsx → fetch(no-store)- searchParams usedPropagation:- affects 8 routesConfidence: Medium
```

---

## 3.2 Cache semantics

```
⚠️ Stale risk (?)Evidence:- fetch("/api/products") uses default cache- no revalidateTag found- no revalidate configConfidence: Medium
```

---

## 3.3 Client boundary

이건 확정 가능

```
✔ Client boundary (High)Evidence:- "use client" in AppShell.tsx- propagates to 32 components
```

---

## 3.4 Revalidation correctness

```
⚠️ Missing revalidation (?)Evidence:- updateProduct() mutates DB- no revalidateTag("products") found- fetch uses tags: ["products"]Confidence: Medium
```

---

## 3.5 Auth / security

```
⚠️ Possible missing auth (?)Evidence:- route path contains /admin- no requireUser()/requireRole found- no auth middleware detectedConfidence: Low
```

---

# 4. Evidence 레벨 구조

각 evidence를 레벨화

```
Direct evidence:- cookies()- "use client"- fetch optionIndirect:- helper function- naming heuristicHeuristic:- route name- file location
```

# 5. Evidence 기반 트리
